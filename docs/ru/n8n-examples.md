# Импортируемые примеры n8n

[English](../en/n8n-examples.md) | [Русский](../ru/n8n-examples.md)

Сначала настройте [n8n Cloud](n8n-cloud.md) или [свой сервер](n8n-self-hosted.md), затем
выберите уровень. Android во всех случаях отправляет один и тот же webhook-контракт;
Telegram необязателен. Каждый JSON содержит весь нужный JavaScript и готов к импорту.
Примеры созданы с нуля: в них заглушки и синтетические данные, а не экспорт личной инсталляции.

## Выберите уровень

| Уровень | Workflow для импорта | Результат | Зависимости |
| --- | --- | --- | --- |
| 1. Базовый: текстовый webhook | [01-webhook-text.json](../../examples/n8n/workflows/01-webhook-text.json) | Проверка события и ACK, без Telegram | Стандартные nodes |
| 2. Базовый + картинки | [02-webhook-images.json](../../examples/n8n/workflows/02-webhook-images.json) | Текст и JPEG/PNG как binary-файлы n8n, без Telegram | Стандартные nodes |
| 3. Telegram: базовый | [03-telegram-text.json](../../examples/n8n/workflows/03-telegram-text.json) | Форматированный текст, разбиение длинных сообщений | Стандартный Telegram node |
| 4. Telegram: картинки на стандартных nodes | [04-telegram-images-standard.json](../../examples/n8n/workflows/04-telegram-images-standard.json) | Текст и отдельные фото/файлы | Только стандартные nodes |
| 5. Telegram: расширенный | [05-telegram-images-advanced.json](../../examples/n8n/workflows/05-telegram-images-advanced.json) | Текст и все картинки в одном Rich Message, сохранение прогресса отправки | Наш node + Data Table, self-hosted n8n |

[05-telegram-cleanup.json](../../examples/n8n/workflows/05-telegram-cleanup.json) — дополнительный
workflow очистки для уровня 5, а не ещё один приёмник. Он импортируется выключенным и с **Dry Run**.
Примеры рассчитаны на n8n 2.38.x. Уровни 1–4 не требуют установки нашего пакета.
Для расширенного варианта нужен Telegram Bot API с [Rich Messages](https://core.telegram.org/bots/api#sendrichmessage) и файловыми блоками, версия 10.3+.

## Импорт и подключение

1. Скачайте выбранный JSON через **Download raw file** на GitHub.
2. В пустом workflow n8n выберите **⋯ → Import from File**. Все примеры изначально неактивны.
3. В **Webhook** создайте или выберите свой **Header Auth** credential:
   **Name** = `Authorization`, **Value** = `Bearer <ваш-приватный-токен>`.
   Токен можно сгенерировать менеджером паролей или `openssl rand -hex 32`.
4. Если такой **Path** уже занят, измените его. У каждого примера свой путь `message487/01-...`.
   Не заменяйте существующий рабочий workflow импортом примера.
5. Для Telegram выполните дополнительную настройку ниже.
6. Опубликуйте workflow и скопируйте **Webhook → Production URL**, а не адрес редактора или Test URL.
7. В Android **Connection** укажите URL, тот же токен **без `Bearer `**, метку устройства и
   включённое **n8n confirmation**. Сохраните подключение. Тест на главном экране отправляет только текст.

В JSON нет IDs/названий credentials, chat ID, адреса сервера, pinned executions, токенов бота,
API-ключей, IDs проекта и таблицы. Предупреждения о ненастроенных credentials после импорта ожидаемы.
[Официальная инструкция импорта](https://docs.n8n.io/workflows/export-import/).

## Уровни 1 и 2: webhook без Telegram

Уровень 1 проверяет событие и возвращает `{status:"accepted", event_id:"..."}`. Если пришли
картинки, их содержимое намеренно не обрабатывается; для изображений используйте уровень 2.
Уровень 2 проверяет изображения и создаёт `image0`, `image1`, … в **Read images → Binary**.
В JSON-выходе остаются текст и метаданные без повторного Base64. Текст без изображений тоже принимается.
ACK в обоих случаях одинаковый.

Эти workflows ничего не отправляют в Telegram, не дедуплицируют события на сервере и не создают
надёжный входящий буфер. История executions нужна для просмотра, это не очередь доставки.
Для обработки вставьте своё действие/хранилище **перед Respond**. Долгую обработку лучше вынести
отдельно: сначала надёжно сохраните событие, затем ACK и фоновая обработка.
После подтверждённого ACK телефон удаляет payload из своей очереди.

## Уровни 3 и 4: стандартный Telegram node

Выполните [настройку бота и credential](n8n-telegram.md). В **Configure** замените
`REPLACE_WITH_CHAT_ID` на свой фиксированный chat ID или `@channelusername`.
Не берите получателя из входящего запроса. Выберите Telegram API credential **в каждом Telegram node**,
а Header Auth — в Webhook.

Уровень 3 отправляет только текст. Уровень 4 добавляет картинки:

| Изображение | Поведение уровня 4 |
| --- | --- |
| Вложение `big_picture` | Отдельное Send Photo |
| Вложения `gallery` | Отдельное Send Photo для каждой картинки |
| Аватар / значок приложения | Отдельное Send Document с подписью роли |
| Прочее или старое вложение | Отдельное Send Document |

Текст и изображения приходят отдельными сообщениями. Встроенная операция media group не
загружает binary-файлы альбомом. Уровню 4 не нужны внешнее хранилище картинок и свои пакеты;
для коллажей и изображений в том же сообщении с текстом используйте уровень 5.

Длинный текст делится по 3500 UTF-16 единиц без разрыва суррогатных пар emoji. Входные `<`, `>` и `&`
экранируются. Встроенный formatter по умолчанию использует **UTC / en-GB** и английские подписи.
При необходимости измените `timeZone`, `locale`, `messageTypes` в **Prepare Telegram text**.
Оставьте **Parse Mode → HTML** и **On Error → Stop Workflow**.
Серверной дедупликации повторов в уровнях 3–4 нет: потеря ACK может привести к повторной отправке.

## Уровень 5: Rich Messages и прогресс повторов

1. Установите [N8nTelegramNode487 v0.2.1+](https://github.com/andre487/N8nTelegramNode487/releases)
   на self-hosted n8n. Лицензия MIT и инструкция установки находятся в отдельном репозитории.
   Приватная установка даёт тип `CUSTOM.telegramAlbum487`; после неё перезапустите n8n.
   Пакет нужен на всех main/worker процессах, исполняющих workflow. Отдельная переменная окружения
   с токеном не нужна: используется существующий Telegram API credential.
2. Импортируйте уровень 5. Выберите Telegram credential в **Send rich message** и **Send text**.
3. В **том же проекте n8n** создайте [Data Table](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.datatable/), например `message487_sent_parts`.
   Добавьте одну колонку **String** с точным именем `part_key`. `id`, `createdAt`, `updatedAt` — системные поля.
4. В **Configure** замените `REPLACE_WITH_CHAT_ID` и `REPLACE_WITH_SENT_PARTS_TABLE_ID`.
   Нужен ID таблицы из URL/selector, а не её название. Для независимо развёрнутых workflows
   используйте отдельные таблицы, чтобы их ключи не пересекались.
5. Опубликуйте workflow. Знак `?` у node означает, что расширение ещё не установлено/не загрузилось.

Все изображения прикрепляются к первому сообщению с текстом:

| Изображение | Поведение уровня 5 |
| --- | --- |
| Big Picture | Блок фото |
| Изображения MessagingStyle | Коллаж; одна оставшаяся картинка — обычное фото |
| Аватар и значок приложения | Свой коллаж внутри того же сообщения, с подписями ролей |
| Прочие или старые изображения | Файловые блоки внутри того же сообщения |

Отдельных медиа-сообщений нет. При длинном тексте следующие текстовые части отправляются отдельно,
без повторения картинок. Telegram-клиент сам выбирает размер, расположение и видимость подписей.
Отправка исходника 100 px не заставляет клиент показывать превью 100 px.
Фото Telegram может обрабатывать; файловые блоки сохраняют семантику отправки документа.

Прогресс хранится по ключу `event_id:номер_части`. **Check already sent** пропускает уже отправленные
части, **Remember part key** выполняется только после успешной отправки. **Respond** срабатывает
после всех частей, в том числе когда повтор уже доставленного события полностью пропущен.
Поиск в таблице заменяет текущие данные: **Restore pending part** восстанавливает текст и binary
из итерации цикла перед отправкой. Не удаляйте этот node.

Это не гарантия exactly-once: креш между ответом Telegram и записью ключа или параллельные запросы
одного события всё ещё могут дать повтор. Поиск и upsert в таблице не являются атомарной блокировкой
доставки. Для более строгих гарантий сериализуйте обработку или используйте транзакционные claims.
На телефоне отдельно работает дедупликация содержимого: fingerprint включает источник, текст и
хеш коллекции закодированных изображений с их ролями и presentation, независимо от порядка.
Сервер различает повторы доставки по event ID, а не по сходству картинок.

### Дополнительная очистка ключей

Импортируйте companion workflow отдельно и укажите в **Configure** **тот же ID таблицы**, что в
уровне 5. Ежедневное расписание выбирает ключи старше 30 дней. Сначала оставьте **Dry Run**, посмотрите
выбранные строки, затем выключите Dry Run и опубликуйте, если такой срок подходит.
После удаления ключа старое событие может быть отправлено повторно. Недоставленные события на
телефоне могут храниться дольше 30 дней: увеличьте срок или оставьте очистку выключенной.
Очистка не удаляет тексты и картинки — в таблице ключей их нет.

## Возможности Android и контракт изображений

В **Sources → Graphics** выбираются JPEG (по умолчанию, качество 80) или PNG, качество JPEG 0–100,
число вложений, максимальная сторона, KiB на картинку и общий объём. PNG сохраняет прозрачность,
JPEG заменяет её белым. Лимиты по умолчанию: 3 вложения, 1024 px, 256 KiB на файл, 512 KiB суммарно
до Base64. Аватары и значки включаются независимо, по умолчанию выключены; число вложений они не
расходуют, но общий байтовый бюджет делят со всеми. Отключение лимитов не отменяет конвертацию формата
и защиту памяти/чтения входных данных. Для Sources также есть opt-in автоматического выбора новых
обнаруженных приложений. Подробнее — [основная документация](../../README.md#delivery-and-data) и экран Sources.

У элемента `images` есть `mime_type`, `width`, `height`, `data_base64`, `kind` (`attachment`,
`avatar`, `app_icon`) и `presentation` (`big_picture`, `gallery`, `file`). У старых изображений
presentation может отсутствовать: примеры считают их файлами. Галерея — наше объединение вложений
MessagingStyle одного уведомления, а не Android album ID. Big Picture и messaging-изображения могут
быть в одном payload. Текст/SMS без картинок не содержат `images`; версия схемы остаётся 1.

**Overview → Send text test** всегда отправляет только текст. В **Connection → Test message**
независимо включаются Big Picture, галерея из двух изображений, аватар и значок. Всё выключено — только
текст. Это не меняет opt-in сбора уведомлений. Используются синтетические карточки и логотип приложения,
с учётом настроек графики. Пользовательские тесты намеренно не подавляются дедупликацией содержимого телефона.

## Проверка синтетическими данными

[text.json](../../examples/n8n/payloads/text.json) подходит всем уровням,
[images.json](../../examples/n8n/payloads/images.json) — уровням с картинками. PNG — синтетические цветные
прямоугольники. Из корня репозитория выполните запрос на **свой** Production URL:

```sh
export MESSAGE487_WEBHOOK_URL='https://n8n.example.org/webhook/message487/YOUR-PATH'
# Задайте WEBHOOK_TOKEN локально: ваш токен без префикса Bearer.
curl --fail-with-body --max-time 10 "$MESSAGE487_WEBHOOK_URL" \
  -H "Authorization: Bearer ${WEBHOOK_TOKEN:?Set WEBHOOK_TOKEN}" \
  -H 'Content-Type: application/json' \
  --data-binary @examples/n8n/payloads/text.json
```

Для изображений замените имя файла на `images.json`. Для **нового** теста задавайте новый `event_id`;
для проверки подавления повторов уровня 5 повторяйте исходный ID. Невалидные основные поля дают HTTP 400,
неверная/отсутствующая авторизация — 401/403. Сверьте точный event ID подтверждения в Journal.
Переключателями Connection можно проверить все варианты картинок с телефона/эмулятора.

Для уровня 5 повторите уже доставленное событие: ACK должен остаться успешным, новых сообщений Telegram
быть не должно. Проверьте текст, каждый тип изображения, смешанный набор, PNG/JPEG и длинный Unicode
с HTML-символами. При ошибке получателя не должно быть accepted ACK; повтор продолжает недоставленные части.
Для реального сбора снимите паузу и выберите источники. Не выбирайте Telegram на телефоне, получающем
сообщения этого бота: иначе возможна петля пересылки.

## Ограничения, приватность и сопровождение

У приложения connect/read timeout по 10 секунд. Большая загрузка или много отправок могут не уложиться;
для тяжёлых сценариев добавьте надёжную входящую очередь и фоновый обработчик, а не ранний ACK.
Telegram ограничивает фото/документы, частоту отправки и Rich Messages, а превью определяет клиент.
Reverse proxy должен принимать chunked JSON и достаточный объём тела; Base64 добавляет примерно треть.
Сетевые ошибки, 408/425/429 и 5xx повторяются; постоянные ошибки/невалидный ACK требуют ручного действия.
Изменение Connection не перенаправляет старую очередь: у событий сохраняется исходный получатель.

В executions могут остаться полный текст, Base64, binary и заголовки авторизации. Ограничьте доступ
и настройте retention. На телефоне картинки лежат в приватных файлах без дополнительного шифрования,
текст и токен шифруются AES-GCM. Payload и картинки удаляются после подтверждённой доставки или ручного
удаления. В самих примерах секретов нет, но настроенный экспорт может содержать имена/IDs credentials
и pinned data: удаляйте их перед публикацией.

JSON генерируется из общих скриптов. После изменений выполните
`python3 scripts/generate_n8n_examples.py`, затем `--check`. CI проверяет синхронность файлов,
валидацию, binary, маршрутизацию, ключи прогресса и оба webhook-примера в DevServer.
