# Проверка релиза Message487

[English](../en/release-testing.md) | [Русский](release-testing.md)

Проверяется конкретный подписанный APK-кандидат, затем опубликованный артефакт.
Зелёный CI, успешный dry-run и тест подключения не заменяют проверку захвата на Android.
Это регламент, а не отчёт о выполненных проверках.

Методика адаптирована из [регламента MegaProxy](https://github.com/andre487/AndroidMegaProxy/blob/main/docs/ru/release-testing.md)
и [f-droid-testing](https://github.com/andre487/f-droid-testing): идентификация APK,
неизменённый рецепт F-Droid, независимые положительные/отрицательные контроли,
проверки обновления, фоновой работы и восстановления. Старые результаты других приложений
не подтверждают работу Message487. Источники и конкретные примеры перечислены в конце.

## Доказательства и статусы

Каждый сценарий на каждом устройстве получает **PASS**, **FAIL**, **BLOCKED**,
**NOT TESTED** или **N/A**. N/A требует причины, связанной с продуктом или платформой;
отсутствие устройства/времени — NOT TESTED. JVM-тест и анализ исходников не заполняют
ячейку проверки на устройстве. Для частичного результата укажите, что именно выполнено.

Запись: ID сценария, время UTC, commit и SHA-256 APK, устройство/ОС, предусловия,
действие, expected/actual, ссылки на доказательства, статус и результат восстановления.
Для доставки сопоставьте синтетический маркер и `event_id` в **Журнале**, HTTP-запросе
и **n8n Executions**; проверьте тело и статус ответа. Отрицательный сценарий требует
исправного положительного контроля до и после. Существенные ошибки авторизации,
утечки и потерю данных воспроизводите дважды с новыми маркерами.

`accepted` означает подтверждение веб-хука, а HTTP 2xx без ACK — только HTTP-успех.
Они не подтверждают Telegram или другой последующий узел: его проверяют отдельно.
Повторная отправка после потери ответа может создать несколько executions с одним
`event_id`; Message487 не обещает exactly-once. Стенд и downstream должны дедуплицировать
по ID, если это требуется сценарию.

Сырые логи, дампы БД/UI, сетевые захваты и n8n executions держите локально в каталоге
0700, чувствительные файлы — 0600. Даже URL веб-хука может содержать секрет.
В Git включайте только проверенные обезличенные выдержки и синтетические фикстуры.
Не отправляйте диагностическое письмо, не загружайте APK на VirusTotal, не публикуйте
issues/релизы и не меняйте внешний F-Droid MR в рамках обычного тестового прогона.

## F-Droid и происхождение APK

В [fdroiddata](https://gitlab.com/fdroid/fdroiddata) выберите build block именно
кандидата для `life.andre.message487`, зафиксируйте recipe SHA, upstream SHA,
fdroiddata/fdroidserver revisions, `Binaries` и `AllowedAPKSigningKeys`, если заданы.
Для внешнего MR проверяйте его текущее состояние; при независимом review требуется
соответствующее приглашение к review. Существующий опубликованный рецепт тоже допустим
как цель проверки; не заменяйте его предполагаемым новым build block.

Используйте официальный `registry.gitlab.com/fdroid/fdroidserver:buildserver`, запишите
фактический digest/platform, штатного пользователя сборки и конфигурацию fdroiddata.
В отдельном checkout выполните применимые команды поддерживаемой версии fdroidserver:

```sh
fdroid readmeta
fdroid lint life.andre.message487
fdroid fetchsrclibs life.andre.message487:VERSION_CODE --verbose
fdroid build --verbose --test --scan-binary --on-server --no-tarball life.andre.message487:VERSION_CODE
```

`VERSION_CODE` заменяется кодом из выбранного recipe. Объясните отличие команды,
если его требует официальное окружение. Сохраните exit codes, source/binary scanner
results и путь APK. Не изменяйте recipe для получения PASS. Предупреждения исследуйте,
а не объявляйте автоматически блокерами; отдельно проверьте updater/APK downloads,
зависимости, бинарные assets и применимость [Inclusion Policy](https://f-droid.org/docs/Inclusion_Policy/).

При воспроизводимой сборке выполните официальный механизм binary comparison/signature-copy
с точным upstream APK и разрешённым сертификатом. Обычный Gradle build и сравнение
SHA-256 APK с разными подписями не заменяют эту проверку.
[Руководство F-Droid](https://f-droid.org/docs/Reproducible_Builds/).
Если matching upstream APK ещё не опубликован, проверка BLOCKED/NOT TESTED;
не публикуйте релиз только ради теста и не объявляйте воспроизводимость заранее.

Для runtime установите именно проверенный подписанный APK; локальный unsigned результат
не обновляет прежнюю signed установку. Если проверяется подпись F-Droid, идентифицируйте
её отдельно. Прочитайте установленный APK через `pm path`/`adb pull` и сверяйте hash
с ожидаемым артефактом на каждом устройстве. Реальная установка клиентом F-Droid нужна
для проверки источника обновлений; установка через ADB не доказывает этот путь.

## Матрица устройств

Сценарии ниже выполняйте на всех четырёх устройствах, где применимы. Для сценария,
недоступного на телефоне, не подставляйте PASS эмулятора. Деструктивные сбои БД/Keystore,
подмену APK/времени, process kill, Doze и искусственные ответы сначала проверяйте
на выделенном стенде. На телефоне без возможности SMS используйте N/A с причиной;
эмуляторная SMS не доказывает доставку от оператора.

| C06 | Отключение источника и пауза при захвате/отправке. Нет новых событий после отключения/паузы; пауза также задерживает старую очередь. Уже выполняющийся запрос может завершиться. После Resume старые события доставляются, пропущенные во время паузы не импортируются. Две ручные проверки подключения не должны подавляться дедупликацией сообщений. |

### Веб-хук, авторизация и очередь

| ID | Действие → требуемый результат |
| --- | --- |
| Q01 | Save/send test, затем реальные capture events через HTTPS. Правильный Bearer в Authorization, JSON schema/поля, уникальный event_id и совпадающий ACK. Device code сохраняется, installation ID стабилен. Journal не показывает тело сообщения. Успех ручного test не доказывает RECEIVE_SMS или listener. |
| Q02 | Правильный → неверный → отсутствующий/некорректный → восстановленный токен. Невалидный ввод не сохраняется; сервер отклоняет неправильный, UI не показывает принятие. Неверная TLS CA/hostname, self-signed без доверия и HTTP в release отклоняются. Редирект не пересылает тело/Authorization на новый адрес. Держите положительные контроли до/после. |
| Q03 | n8n ACK: чужой/отсутствующий event_id, неверный status, malformed/слишком большой JSON; generic webhook с ACK выключенным. HTTP 2xx с неверным ACK — BLOCKED и ручной retry, а generic 2xx — HTTP_SUCCESS. Отличайте отказ клиента от успеха выполнения n8n error-workflow. |
| Q04 | Timeout/network failure, HTTP 408/425/429/5xx → очередь повторяет; прочие HTTP failures → ручное исправление/retry. После восстановления сохраняются event_id, тело, старый URL/токен/ACK. Ответ потерян после приёма: возможен повтор на сервере, ID прежний. Нет обещания точного времени WorkManager retry. |
| Q05 | Создайте offline очередь на endpoint A, смените настройку на B. Старые события идут только на A с прежними реквизитами; новые — на B. Ротация токена в UI не исправляет старый encrypted envelope. Используйте отдельные тестовые endpoints; при необходимости старые события явно удаляют, а не тихо перенаправляют. |
| Q06 | Retry now, удаление тестовой записи, быстрые повторные действия и открытый detail при смене состояния. Нет дублирования локального события/потери очереди; активную отправку нельзя удалить как свободную запись. После acceptance payload удаляется из активной записи, metadata остаётся ограниченной; logical delete не доказывает физическое стирание. |
| Q07 | Offline enqueue → обычное завершение процесса/rotation/relaunch → восстановление сети. Проверить сохранность encrypted payload и доставку, включая очередь предыдущей версии. Недоступный Keystore/повреждённое хранилище — изолированный сценарий: нет отправки мусора или тихого удаления; ошибка видна. Успех Robolectric не доказывает настоящий Keystore. |

### Приватность и диагностика

| ID | Действие → требуемый результат |
| --- | --- |
| D01 | Синтетические маркеры в body/title/sender/URL/token/device code/ID/response. Искать в app logs, crash file, ZIP и доступных системных логах; нет утечки исключаемых полей. Неверные APK сначала JVM/изолированный эмулятор. Fixture-версии не публиковать и production versionCode не менять ради проверки. |
| U03 | GitHub download → отдельное Install, отказ/выдача unknown-source permission, возврат из Settings, Cancel/успех, rotation/background. Сверить установленную версию/hash/подпись и доставку после установки. F-Droid открывает страницу, установку выполняет клиент. Разные подписи не обновляют друг друга; не удалять приложение как первое «исправление». |
| U04 | Reminder permission/channel, Open/Skip/Disable, manual check после Skip, выключение при running job, reboot. Проверить повтор через неделю и отсутствие раннего повторения управляемым временем на эмуляторе. Принудительный запуск и simulation не считать естественным daily/weekly результатом. |
| R01 | Dry-run с явно заданной предполагаемой версией: генерация EN/RU и проверки чтения, без файлов/релизной ветки/PR/merge/tag/Release. Пустое поле CI означает обычный CI. Перед/после сравнить refs/PR/releases; mock-тест и live run отметить отдельно. Dry-run не доказывает права записи, signing или прохождение ruleset. |
| R02 | Перед реальным выпуском прочитать EN/RU changelog, сравнить versionName/code, историю и список файлов релизного PR. Gate должен ждать полный CI конкретного head/base; старый/skipped CI не принимается, изменённый main/head останавливает merge. Эти отказные случаи тестировать локально с mocks, не ломая production правила. |
| R03 | Только после отдельного запуска выпуска проверить фактический merged commit/tag, tree и источник опубликованных APK, checksum/подпись, постоянный и versioned URL, changelog обеих локалей. Сверить APK с проверенным кандидатом; различающийся артефакт требует расследования/retest. F-Droid build/publication подтверждается отдельно. |

## Завершение и решение

Сначала APK identity, доставка test/SMS/notification на каждом устройстве, отрицательная
авторизация/ACK, offline recovery и migration. Затем фон, updater, приватность и OEM/UI.
При сокращении матрицы оставляйте NOT TESTED; оно не становится PASS. Для небольшого
follow-up опишите diff, обязательные соседние регрессии и границы сокращённого прогона.
Старые phone results не переносите на новую версию даже при неизменённом UI.

В конце остановите только созданные стенды/captures, удалите только свои ADB forwards/reverses,
probe APK и синтетические события; верните сеть, permissions, источник/автопроверку,
батарею, экран/шрифт/язык, Auto Blocker и исходные настройки приложения. Не удаляйте
чужие workflow/volumes и личные сообщения. Удаление локального события не удаляет
копию из n8n/downstream: очистите синтетические executions отдельно. Запишите остаточные
изменения и проверьте устройства после восстановления.

Не рекомендовать выпуск при потере очереди/секретов, неверной подписи, обходе авторизации,
утечке исключаемых данных, необъяснённых падениях или неработающем захвате/доставке
на поддерживаемом устройстве. Критическая непроверенная миграция или BLOCKED gate
означают **РЕЛИЗ НЕ ПРОВЕРЕН**. Для каналов GitHub и F-Droid фиксируйте отдельную готовность.
Исправление: минимальная отдельная ветка, воспроизведение/регрессионный тест, новый APK,
повтор affected и соседних сценариев; старый FAIL остаётся до retest.

Отчёт — `docs/reviews/release-YYYY-MM-DD.md`, только обезличенный материал:

```text
Кандидат: commit, версия/код, SHA-256, сертификат, канал/происхождение APK
Окружение и устройства: фактические параметры и ограничения
Команды/CI/F-Droid: версии инструментов, recipe/image digest, результаты
Матрица: ID | устройство | PASS/FAIL/BLOCKED/NOT TESTED/N/A | доказательства
Находки: expected/actual, серьёзность, контроли, функция, retest commit/APK
Восстановление: ресурсы, что удалено/возвращено, остаточные изменения
Решение: готовность GitHub/F-Droid, blockers и непроверенные сценарии
```

До публикации устройство должно проверять подписанный кандидат из релизного PR;
для проверки changelog до merge нужен human review gate в [релизном флоу](release-automation.md).
Постпубликационный R03 — дополнительная проверка, а не разрешение выпускать непроверенный APK.
В рамках подготовки этого регламента тесты на устройствах не выполнялись.
