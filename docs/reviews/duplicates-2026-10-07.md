# Исследование дубликатов — 2026-10-07

Ветка: `investigate/duplicate-delivery`, база `5558816` (`main`, PR #25).

## Вывод

Основной подтверждённый механизм: один webhook с неизменным `event_id` приходит
повторно, а workflow каждый раз отправляет новое сообщение Telegram. Дедупликация
захвата в Android не предназначена для подавления повторных попыток доставки уже
созданного события. В рабочем workflow отсутствует идемпотентная обработка `event_id`.

Дополнительно получена диагностика телефона: в сопоставленных примерах приложение
записывает `NETWORK_ERROR` после первой попытки и повторяет доставку, пока не
получит `ACCEPTED`. Точный вид сетевой ошибки не установлен: исключение в этой
ветке WebhookClient не сохраняется. Успех узла Respond не доказывает получение
ACK телефоном.

Один `event_id`, одинаковое тело, `occurred_at = 2026-10-07T07:11:09.071Z`.

| Execution | Начало, UTC | Длительность | Telegram message_id |
| --- | --- | --- | --- |
| 893 | 07:11:10.254 | 2258 мс | 40018 |
| 894 | 07:11:51.088 | 2147 мс | 40019 |

Ещё одно событие поступило в executions 873–876 четырежды. Первые три запроса
начались 6 октября в 11:01:18.513, 11:01:48.463 и 11:02:18.513 UTC,
четвёртый — в 11:21:03.643. Telegram создал сообщения 39998–40001.
Все executions имеют `mode = webhook`, `retryOf = null`: это новые входящие
HTTP-запросы, а не сохранённый n8n retry execution. User-Agent соответствует
Android HttpURLConnection; один идентификатор устройства во всей выборке.
Автоматический повтор, ручной повтор и повтор после восстановления очереди
по одним серверным данным однозначно не различить.

Запуски 896 и 897, совпадающие по отображаемой секунде, дубликатами этой категории
не являются: различаются `event_id`, текст, заголовок и точное время события.
Совпадение времени в списке executions само по себе не является свидетельством дубля.

Обе пары — notifications `com.domonap.app`. Формат Telegram округляет время

должны подавляться. Событий с разными ID и полностью одинаковыми устройством,

## Диагностика телефона

Прочитаны `diagnostic.log`, `environment.txt` и пустой `crash-latest.log` из
предоставленного каталога `message487-diagnostics-0dbe63c5-b8aa-4ee4-b939-bdcb9cdcf462`.
Архив указывает release 1.0.0 (versionCode 6), Android 16/API 36, ACK включён,
приложение не на паузе. Лог содержит 4187 строк с 9 сентября по 7 октября;
версия в environment описывает состояние при экспорте, а не каждый старый запуск.

Для executions 893/894 последовательность телефона однозначна по времени:

| Время телефона, UTC, 7 октября | Событие |
| --- | --- |
| 07:11:09.287605 | Единственный `EVENT_QUEUED` |
| 07:11:09.304012 | `DELIVERY_STARTED`, первая попытка |
| 07:11:20.750003 | `DELIVERY_FINISHED outcome=NETWORK_ERROR`, HTTP-кода нет |
| 07:11:21.107714 | `DUPLICATE_SKIPPED`: повторный захват подавлен |
| 07:11:50.944631 | `DELIVERY_STARTED`, повтор доставки |
| 07:11:53.270662 | `DELIVERY_FINISHED outcome=ACCEPTED http=200` |

Первая попытка телефона заняла около 11.446 секунды, хотя execution 893
успешно завершился на сервере в 07:11:12.512. Повтор соответствует execution 894.
Нового `EVENT_QUEUED`, ручного повтора, старта приложения или падения в этом
интервале нет. Это подтверждает автоматический повтор после сетевой ошибки,
при этом повторный захват уведомления отдельно был подавлен.

Для executions 873–876 (6 октября) телефон записал:

| Начало попытки, UTC | Конец попытки, UTC | Результат |
| --- | --- | --- |
| 11:01:18.332911 | 11:01:20.018022 | `NETWORK_ERROR` |
| 11:01:48.362791 | 11:01:51.209457 | `NETWORK_ERROR` |
| 11:02:18.362734 | 11:02:26.354947 | `NETWORK_ERROR` |
| 11:21:03.431957 | 11:21:05.831900 | `ACCEPTED`, HTTP 200 |

Таким образом, n8n отправил одно событие четырежды, пока телефон не зафиксировал
успешный ACK. Это не ручные повторы: в соответствующем интервале нет `MANUAL_RETRY`.
В журнале после 5 октября 16:00 UTC всего 10 результатов `NETWORK_ERROR`
и 37 `ACCEPTED`; TIMEOUT и INVALID_ACK в этом интервале нет.

ID события в диагностическом логе намеренно отсутствует, поэтому связь с n8n
установлена по изолированным последовательностям времени, а не по ID из лога.
При нескольких параллельных отправках такое сопоставление неоднозначно.

## ACK и ограничения диагностики

Рабочая цепочка: Webhook → Prepare Telegram text → Telegram → Respond.
Respond настроен на JSON, HTTP 200 и
`{ status: 'accepted', event_id: $('Webhook').first().json.body.event_id }`.
Выражение использует исходный Webhook, а не результат Telegram. Ошибка ссылки
на `$json.body` в проверенных конфигурациях отсутствует.

WebhookClient использует таймауты подключения и чтения по 10 секунд.
Outbox сохраняет исходные payload и `event_id` между попытками; TIMEOUT и
NETWORK_ERROR ведут к RETRY. WorkManager использует уникальную работу на событие
и экспоненциальную задержку с начальным значением 30 секунд.

Из 49 первых executions повторявшихся событий только два длились не менее
10 секунд; диапазон длительности 515–12756 мс. Поэтому объяснять все повторы
медленным workflow нельзя. Полученный клиентский лог подтверждает сетевые ошибки
в сопоставленных примерах, но не определяет их уровень: TCP, TLS, чтение ответа
или другая IOException. В WebhookClient IOException преобразуется в NETWORK_ERROR
без записи типа исключения и этапа запроса; безопасный стек для этой ошибки
не попадает в DiagnosticLog. По этим данным нельзя выбрать конкретное исправление
транспорта или обвинить Caddy, n8n либо мобильную сеть.

Входной Caddy содержит только `reverse_proxy 127.0.0.1:5678`; access log
не настроен. В его journal за интервал 07:10–07:13 UTC 7 октября записей нет.
Сохранённый output Respond содержит входные данные Telegram, а не фактически
полученный телефоном HTTP-ответ. Сам execution не позволяет проверить получение ACK.

## Следующие действия

1. Для защиты от доказанного механизма нужен постоянный учёт `event_id` на
   принимающей стороне с уникальным ограничением БД. Уже обработанный ID должен
   получить тот же успешный ACK без повторной отправки Telegram. Простая проверка
   «найти, затем вставить» не защищает от одновременных запросов.
2. Если ACK переносится перед Telegram, сначала необходимо надёжно сохранить
   событие в очередь. Простой перенос Respond вперёд создаст риск потери сообщения
   после удаления payload из очереди Android. Для больших сообщений нужен также
   учёт отправленных частей. Сбой между успешной отправкой Telegram и фиксацией
   результата всё ещё оставляет неоднозначность; Telegram sendMessage не даёт
   гарантии exactly-once по нашему `event_id`.
3. Клиентский архив уже подтвердил NETWORK_ERROR для проверенных повторов.
   Для уточнения сетевой причины следующая минимальная доработка диагностики —
   сохранять безопасный тип/стек IOException и фиксированный этап запроса,
   без текстов исключений, URL, токенов и payload. Существующий safeStackTrace
   позволяет не добавлять произвольные сообщения исключений. После успешного
   повтора прежний outcome в записи очереди заменяется последним.
4. Проверить установленную версию приложения и включённое окно дедупликации
   уведомлений. Поведение двух пар от 4 октября не доказывает дефект текущей версии.

В рамках исследования исправления Android и рабочего n8n не применялись.
Увеличение таймаута или отключение повторов не устраняет отсутствие
идемпотентности; отключение повторов создаст риск потери сообщений.
